# 训练游戏操控链审计：四个产品侧方案 vs. 现状

- 审计对象：`src/game/gazeGame.ts`（全文 721 行）、`src/game/presenter.ts`、`src/gaze/model.ts`（测量层约束）、`src/ui/app.ts`（接线与门控）、`src/protocols.ts`（校准协议）
- 方式：**只读静态审计**，未运行程序、未做性能剖析、未改任何代码
- 结论口径：所有"度 ↔ 像素"换算都基于 `docs/RESULTS.md` 记录的实测机器
  （15.6" / CSS 1442×901 / 观看距离 500 mm），据此
  `mmPerPx ≈ 0.233 mm/px`、**1° ≈ 37.4 px ≈ 8.7 mm**。
  换机器时下表所有像素值按 `pxPerDeg` 等比缩放，角度值不变。

## 0. 结论摘要

1. **四个提案里真正做过的只有"校准"，而且做得比提案更重**（13 点 + 留出点 + 两轮热身 + 逐眼岭回归 + LOOCV + 坏点自动补测）。缺口不在"点够不够"，在**游戏内零位的维护方式**。
2. **死区"名义存在、实际无效"**：`degMm(0.2)` = 7.5 px，而且它的语义是"不修正"而不是"站住不动"。
   用户提的 15 px（0.40°）同样无效——**这两个数字都比 2–4.5° 的噪声地板小一个量级**。
3. **"滑动窗口平滑"没有实现**，现有的是两级串联的指数/α-β 滤波，而且**滤波的时序假设是错的**：同一帧相机样本会被重复积分 2–4 次，等效把位置增益放大到 0.86、速度增益翻倍。这是"抖 + 拖"的直接来源。
4. **"星星吸附"一行都没写**。而且现有捕获半径（5.5°→3.2°）**已经**是星星可视半径（1.2°）的 4.6 倍，缺的不是"放宽判定"。
5. **一个贯穿全篇的量化判断：现有三个阈值分别落在噪声地板的"远下方、正中间、正中间"**，所以要么永不触发，要么被噪声触发。这是"用产品手段掩盖精度不足"最该先修的东西——不是加功能，是把阈值重新摆到噪声地板的正确一侧（见 §2.3）。

用户四条实测反馈**全部都能定位到具体代码行**（其中"越到后面越偏"有一半是难度曲线造成的感知效应，见 FM-5）：

| 反馈 | 最可能的主因 | 证据 |
|---|---|---|
| 盯着中心点，火箭却在另一个点 | 加油锚定把"提示语/HUD/走神"的样本当成"看中心"样本，算出一个错零位 | `gazeGame.ts:270-271, 289-313`；提示语位置 `index.html:232-233` + `styles.css:458-478` |
| 来回动（在某个错点附近） | 锚定零位被整体替换（step 变化）+ 3° 扫视吸附落在噪声带内被误触发 | `gazeGame.ts:306-313, 319`；`gazeGame.ts:192, 121-128` |
| 火箭不跟 | 双级平滑 + 同一样本重复积分 → 总滞后 250–400 ms；另有 20–35% 的时间被"加油停靠/待加油"占用 | `gazeGame.ts:365, 105-141`；`gazeGame.ts:353-354` |
| 越到后面越偏 / 边缘不准 | 难度曲线把捕获半径收到 3.2°（进入噪声带）；零位只做平移、不做增益；外侧校准点本身 LOO 就差 | `gazeGame.ts:381-384`；`gazeGame.ts:621-626` |

### 2.2 噪声地板

- 校准交叉验证（LOOCV）：**2.2–4.5°**（`docs/STATUS.md:60`，十余次校准）
- 旧版游戏"追上瞬间误差"：**2.89°**（`docs/STATUS.md:61`）
- 练习者自己的重复性：会话内 ≈1.15°（3 轮取中位，`docs/STATUS.md:59`），但那是**平均值**，单帧不行

**游戏是逐帧绝对定位，没有平均的机会**，所以对游戏而言噪声地板取 **2–4.5°/帧**，不是 1.15°。

### 2.3 三个阈值 vs. 噪声地板（本审计的核心表）

| 阈值 | 现值 | 相对 2–4.5° 噪声 | 结果 |
|---|---|---|---|
| 死区 | 0.2° | **5–10%** | 永不触发 = 没有死区 |
| 扫视吸附 | 3.0° | **67–150%** | 落在噪声带里 → 噪声被当成扫视，**随机瞬移** |
| 捕获半径（终局） | 3.2° | **71–160%** | 落在噪声带里 → 后期"该中不中" |
| 用户提的死区 | 0.40° | 9–20% | 改进方案本身也不够 |
| 用户提的磁吸 | 1.34° | 30–65% | 小于噪声 → 触发不了 |

> 一句话：**产品侧参数必须按"噪声地板"的倍数来摆，而不是按"看上去差不多"来摆。**
> 死区 ≥1.5°、吸附 ≥6°、捕获 ≥5° 才是安全的落点（分别约为噪声上界的 0.3×、1.3×、1.1×）。

## 3. (a) 四条方案各自实现到什么程度

### 3.1 方案①：死区（"两次坐标差 < 阈值就别动"）

**实现度：20%（有形无实）**

- 构造：`gazeGame.ts:192` `new GazeFilter(degMm(3), degMm(0.2))`
- 逻辑：`gazeGame.ts:129-133`

```ts
if (r < this.deadMm) {
  this.x = px;          // px = x + vx*dt，是"预测位置"
  this.y = py;
  return { ... };
}
```

三个问题：

1. **语义不对**。它抑制的是"修正量"，不是"输出"。死区内位置仍然按上一帧速度继续走（`px = x + vx*dt`），
   速度也不清零。所以它不是"火箭保持静止"，而是"不再纠偏"——噪声在死区外积出来的速度会继续推着走。
2. **阈值不对**。0.2° = 7.5 px = 1.7 mm，是噪声的 5–10%。而 `r` 是"预测值 − 测量值"的残差，
   在噪声 2° 的量级下几乎不可能低于 0.2°。这个分支在真实数据里基本不执行。
3. **作用点不对**。真正需要"站住"的是**火箭的输出**，而火箭在 `gazeGame.ts:363-375` 还有一级 `k` 平滑；
   死区加在滤输入端、又被后级平滑抹一遍，两层都在追一个抖动的目标。

> 用户提的 15 px 也不行：15 px = 0.40°，仍只有噪声的 9–20%。要用"打点"的方式掩盖 2–4.5° 的抖动，
> 死区必须 ≥1.5°（≈56 px），并且必须是**迟滞**（进入 1.5°、退出 0.6°），否则会在边界上抖。

### 3.2 方案②：滑动窗口平滑（最近 5–10 帧取平均）

**实现度：0%（结构不同，且时序有 bug）**

现有的是两级串联：

| 级 | 位置 | 形式 | 参数 |
|---|---|---|---|
| 1 | `GazeFilter.update` `gazeGame.ts:105-141` | α-β（位置+速度） | α=0.62、β=0.16（`134-139`） |
| 2 | 火箭跟随 `gazeGame.ts:365` | 一阶指数 | `k = 1 - 0.92^(dt/16.7)`，每帧 ≈0.08 → 时间常数 ≈12.5 帧 ≈200 ms |

没有窗口、没有中位数、没有帧数统计、没有自适应。**而且第 1 级的时序假设是错的**：

- `face.ts:104-106` 用 `video.currentTime` 去重，相机 30 fps → `live[]` 每 33 ms 才更新一次；
- 游戏主循环是 rAF（`gazeGame.ts:539`），60–120 fps → **同一帧样本被 `filter.update` 消费 2–4 次**（`gazeGame.ts:360`）；
- `dt` 传的是 rAF 的间隔（≈16 ms），不是样本间隔（≈33 ms）。

后果：每个新样本要经历 2–4 次"预测 + 修正"，位置增益从设计的 0.62 变成 `1-(1-0.62)² ≈ 0.86`，
速度项 `β·r/dt` 每个样本被踢 2–4 次。**这正是"抖 + 拖"同时出现的机理**：
位置跟得快（0.86）但速度噪声大、过冲后又回拉。

> 结论：再叠一层 5–10 帧窗口只会更糟——30 fps 下 5 帧对称窗口 = 额外 66 ms 延迟、10 帧 = 133 ms，
> 叠在现有的 200 ms 上就是 300–350 ms，用户会直接说"更不跟了"。
> 正确方向是**改成一级自适应滤波**（one-euro），不是再加一级。

### 3.3 方案③：星星吸附（近 50 px 且视线有趋势时放宽判定/吸过去）

**实现度：0%**

- 捕获判定只有一句距离比较：`gazeGame.ts:388`
  `Math.hypot(rocket.x - sx, rocket.y - sy) <= captureMm`
- 没有趋势判据、没有吸引、没有辅助；
- `gazeGame.ts:488-495` 那个逐渐变亮的外圈**不是**吸附，它是"星星快过期了"的视觉提示（`age > 3000` 后随时间变亮），只影响观感不影响判定。

而且需要认清一点：**现在缺的不是"放宽判定"**。

| 对象 | 半径 | 倍数 |
|---|---|---|
| 星星可视半径 | 1.20° / 45 px | 1× |
| 开局捕获半径 | 5.50° / 206 px | **4.6×** |
| 20 分捕获半径 | 3.20° / 120 px | **2.7×** |

也就是说玩家"看着离星星还差一截"时其实早就判中了。用户抱怨"追不上"，根源在**瞄准（aim）**，不在判定。
真正该做的是：**把捕获半径固定在噪声地板上方**（≥4.5–5°），再考虑"趋势门控的弱吸附"作为锦上添花。

> 用户提的 50 px = 1.34° 也偏小：它小于 2.89° 的实测命中误差，等于什么也没吸到。
> 若要做，半径取 150–200 px（4–5.4°），并且**必须**用"视线正在朝星星移动"做门控。

### 3.4 方案④：9 点校准（开局盯点并点击，拟合个人映射）

**实现度：120%（早已超额实现，不需要重做）**

| 环节 | 位置 | 现状 |
|---|---|---|
| 热身 | `protocols.ts:60-82` | 5 点 × 2 轮，专门解决"前 5 个点误差 8°"的边做边学问题 |
| 校准点 | `protocols.ts:34-48` | **13 点**（中心→4 格心→4 边中→4 角），不是 9 点 |
| 留出验证 | `protocols.ts:52`、`96-106` | 1 个不参与拟合的验证点 |
| 拟合 | `app.ts:838-1011`、`model.ts:121-225` | 逐眼岭回归 + 去收缩线性校正 |
| 交叉验证 | `app.ts:900-920` | 留一点 × 13，逐点报错 |
| 坏点补测 | `app.ts:775-790` | 只补测漂移点，2–5 秒 |
| 游戏内二次零位 | `gazeGame.ts:286-330` | 每次加油重估 `offL/offR`（平移） |
| 准入 | `app.ts:1254` | 没有校准不能开始游戏 |

**真正的缺口不在"点"，在两件事：**

1. **只有平移，没有增益**。`offL/offR` 是"raw 预测的均值"（`gazeGame.ts:306-313`），
   只把零位搬回中心，对"中心准、边缘偏"的尺度/非线性误差**完全无感**。
   用户说"边缘不准"时，这套机制帮不上忙。
2. **重新校准是"整体替换"，且入口很松**（详见 §4 FM-1）。
   每次加油把零位整体换掉，一次坏样本就能把全屏的瞄准整体推走。

结论：**不建议再写一套 9 点流程**（会与现有 13 点冲突、增加一次 30 秒的疲劳点），
应当把力气花在"游戏内零位怎么维护"上——见建议项 P1。

## 4. (b) 真实失效模式（按影响手感排序）

> 排序依据 = "这一条发生时，玩家还能不能玩"。恒定偏置 > 抖动 > 跳点 > 难度错配 > 体感设计。

### FM-1 ★★★★★ 加油锚定会把"看提示语/HUD/走神"的样本当成"看中心"→ 学出错误零位

**症状**：正对中心，火箭却稳定停在另一个点；每次加油后那个点还会换。

**证据链**：

- 采样窗以**加油站（真实中心）**为圆心，首次 15°、之后 8°（`gazeGame.ts:265-271`）；
  15° = 574 px，**覆盖整个屏幕高度**（半高只有 450 px = 12.0°）。
- 采样条件只有 `hasGaze && goodSample`（`gazeGame.ts:289`），**不检查 `gaze.valid`**——
  眨眼帧、头位超限帧、距离超限帧全都进均值。
- 提示语 `#testPrompt` 是 HTML HUD，固定在屏幕顶部（`index.html`、`styles.css:458-478`），
  在 901 px 高的屏幕上位于中心上方约 **11°**；`drawHud` 的分数在中心上方 **11.3°**、
  燃料条在 **9.0°**（`gazeGame.ts:669-693`）。
  → 首次锚定的 15° 窗口把这三样全部纳入"中心样本"；之后的 8° 窗口刚好把它们挡在外面（9° > 8°）。
- 最讽刺的一点：**进入校准的瞬间提示语从"看红色加油站"变成"正在校准·看住中间的绿圈"**（`gazeGame.ts:338-345`），
  这句话本身就把眼睛吸向屏幕顶部。
- 提交门限：`enough` 要求每眼 30 个样本（`gazeGame.ts:79, 303`），
  但**实际提交只要 12 个**（`gazeGame.ts:306, 310`）；超时路径（`304-305`，最长 9 s）
  会用一份 12 样本、可能混着抬头看提示语的均值直接覆盖零位。
- 均值是**普通算术平均**，没有中位数、没有截尾、没有离散度检查。

**量化**：若 3.6 s 窗口里有 0.4 s 在看 11° 上方的提示语，零位就被拉高 `0.4/3.6 × 11° ≈ 1.2°`；
若小孩先盯着提示语读了两秒，就是 6° 量级的错零位。而**平滑对恒定偏置完全无效**——
这是最该先修的一条。

### FM-2 ★★★★☆ 同一相机样本被重复积分 + 双级平滑 → 抖动与滞后并存

**症状**：火箭"跟不上"、转折时甩尾、静止时又轻微游走（"来回动"）。

**证据**：`gazeGame.ts:360`（每帧都调 `filter.update`）× `face.ts:104-106`（样本 30 Hz）×
`gazeGame.ts:539`（循环 60–120 Hz）× `gazeGame.ts:365`（第二级 k=0.92）。
外加 MediaPipe 同步推理在主线程（`face.ts:108`、`app.ts:445`），推理尖峰直接吃帧。

**量化**：设计 0.62 的位置增益实际约 0.86；β 的速度注入翻倍；
两级时间常数 ≈ 200 ms（火箭）+ 若干帧（滤波），加上相机 33 ms + 推理 10–40 ms + 显示 1 帧
→ **端到端 250–400 ms**。人眼追踪目标是 0–100 ms 的期待，300 ms 就是"脱手"。

### FM-3 ★★★★☆ 3° 扫视吸附落在噪声带里 → 噪声被当成扫视，产生随机瞬移

**症状**：静止注视时火箭偶尔"啪"地跳 2–3°，然后慢慢回来。

**证据**：`gazeGame.ts:121-128`（`r > degMm(3)` 就整体吸附并把速度清零）。
噪声地板 2–4.5°，阈值 3° 正好在带内 → 每次噪声尖峰都可能触发一次"瞬移 + 速度清零"，
表现为卡顿和来回跳。**这是"来回动"的第二个来源，与 FM-1 叠加。**

### FM-4 ★★★☆☆ 眨眼/无效帧仍然驱动火箭

**症状**：眨眼瞬间火箭弹开，睁眼后慢慢回来；偏头、后仰时整段漂走。

**证据**：`gazeGame.ts:246-257` 只看 `predMm` 是否存在，不看 `gaze.valid`；
`app.ts:1249` 把 `quality.ok` 传进来了，但没人用。
眨眼只置 `closed` 标志（`face.ts:156-158`），虹膜点照常输出 → 预测照常计算（`app.ts:501-511`）。
而 `app.ts:407` 对 `blink` 的定义是"只算软失败"（`ok` 里排除 blink，`432-433`），
连 `quality.ok` 都是 true，所以就算接入 `valid` 也挡不住眨眼。

### FM-5 ★★★☆☆ 难度曲线与噪声预算错配："越到后面越偏"一半是错觉

**证据**：`gazeGame.ts:381-384`
`captureDeg = 5.5 - 2.3·min(1, score/20)`，`lifeMs = 6000 - 1500·min(1, score/20)`。

- 得分 10 时捕获半径 = 4.35°，已经**低于** 4.5° 的最坏校准误差；
- 得分 20 时 = 3.2°，是实测命中误差（2.89°）的 1.1 倍 → 命中基本靠运气；
- 星星寿命同时从 6 s 缩到 4.5 s，等于"容差变小 + 时间变短"双重收紧。

**关键认知**：绝对误差很可能一直没变，是**容差在缩小**，所以用户感觉"越到后面越偏"。
这是产品曲线的问题，不是模型的问题——也就意味着可以用产品手段解决（见 P3）。

### FM-6 ★★☆☆☆ "待加油"阶段星星被隐藏，但仍在计分/过期

**证据**：星星的绘制条件是 `launched && !needRefuel`（`gazeGame.ts:471`），
但捕获/过期的判定条件是 `launched && !refuelling`（`gazeGame.ts:380`）。
`needRefuel = phase !== "idle"`（`334`）覆盖了 `prompt` 阶段，而 `refuelling` 只等于 `phase === "refuel"`。
→ **在"待加油"这段时间里，星星不可见却可以被收集、也会超时**，分数会莫名其妙地涨。
逻辑 bug，与手感无关但会污染训练数据（`hits/trials` 口径）。

### FM-7 ★★☆☆☆ 双眼无条件算术平均，把已知更差的那只眼算进一半权重

**证据**：`gazeGame.ts:251-256`（两眼平均，注释解释了为什么不逐帧选眼）。
但 `docs/STATUS.md:81` 明确记录"图像左眼系统性偏差……三项指标都指向同一只眼更差"。
平均能压掉不相关噪声（÷√2），但**压不掉相关偏置**，还会把差眼的额外偏置摊进瞄准点
（跨会话偏置实测可达 ±5 PD ≈ 2.9°，`docs/STATUS.md:80`）。

同时 `GameOptions.dominantEye`（`gazeGame.ts:27`）只用于分视呈现（`155-159`），
**没有参与瞄准**——一个现成的、零成本的先验被浪费了。

### FM-8 ★★☆☆☆ 几何一致性：全屏切换前后的 `innerWidth/Height` 可能不一致（待验证）

**证据链**：

- `computeGeom` 用 `window.screen.width/height` 算 `mmPerPx`（`app.ts:84-98`），这是个常量；
- 校准阶段 `runner.enter()` **先**记录 `window.innerWidth/Height`（`runner.ts:57-58`），
  **后**才 `requestFullscreen()`（`runner.ts:63`），且全程**没有 resize 监听**（全仓库搜索无 `resize`）；
- `#testCanvas` 是 `width:100vw; height:100vh`（`styles.css:443-456`），
  如果 canvas 的 backing store 是"全屏前"的尺寸，画面会被 CSS 拉伸；
- `targetMmFromNm` 用 `runner.width/height` 折算靶点毫米（`app.ts:527-532`），
  而玩家实际看到的光点在 CSS 拉伸后的位置上。

若全屏前后 `innerHeight` 差 10%（窗口模式有浏览器工具栏很常见），
则 y 方向的标签与实际视角差 10% → **纵向增益误差**，越靠边越偏。
`gazeGame.ts` 稍好（`174` 请求全屏、`176` 等 280 ms 再 `sizeCanvas`），但仍是竞态。
**这条是本次审计里唯一需要跑一次来确认的**：加一行日志打印校准前后与游戏开始时
的 `innerWidth/Height` 和 `canvas.width/dpr`，10 分钟即可排除或坐实。
若坐实，它比任何滤波参数都值钱，因为它同时解释"边缘不准"和"中心还行"。

### 5.1 自动游玩风险的三条护栏（任何"放宽判定"的改动都要配）

1. **趋势门控**：只在"视线在最近 150 ms 内朝星星方向移动且速度 >2°/s"时放大容差；
   停住不动时**不**放大。
2. **未移动命中率**：命中前 300 ms 内视线位移 <1° 记为 suspicious。
   这个指标 <5% 才说明磁吸没被滥用（`hitErrors` 已有采集管线，`gazeGame.ts:394-396`）。
3. **导出 `meanHitErrorDeg` 与 `anchor*Deg` 的联动检查**：结果卡片已经在看这两个数
   （`app.ts:1156-1161`，锚定 >2° 会标黄）。如果命中误差一直高于 4°，说明问题在瞄准而不在判定，
   此时**继续放宽判定只会掩盖问题**。

### 5.2 不建议做的事（会踩的坑）

| 想法 | 为什么不行 |
|---|---|
| 直接上 5–10 帧滑动平均 | 30 fps 下追加 66–133 ms 延迟，叠在现有 200 ms 上会变成"更不跟" |
| 把死区调到 15 px（0.4°） | 仍只有噪声的 9–20%，等于没做；要 ≥1.5° 且必须迟滞 |
| 把捕获半径再放大（>6°） | 已是星星半径 4.6 倍，再放大就变成"随便看看就中" |
| 重做一套 9 点校准 | 已有 13 点 + 留出 + 补测；重复建设还会多一次 30 秒疲劳 |
| 在 α-β 上再叠一层平滑 | 误差源是时序不是阶数，叠层只会增加相位滞后 |
| 用 `score` 继续收紧难度 | 把容差收到噪声带里，用户只会得出"这东西不准"的结论 |

### P1（最高）— 把"加油锚定"从"算术均值"改成"鲁棒零位"

**改哪里**：`GazeGame.run()` 的 refuel 段（`src/game/gazeGame.ts:265-330`），
以及常量 `src/game/gazeGame.ts:79-82`。

**怎么改**：

2. 两遍法：先对窗口内全部样本**按 x、y 各取中位数**，再剔除偏离中位数 >1.2° 的样本，
   余下取截尾均值作为新的 `offL/offR`。这样模型有几度的绝对偏置也能采到，
   而"抬头看提示语/看分数"的少量样本会被当作离群点丢掉。
3. 提交条件：`nL ≥ 30 && nR ≥ 30 && MAD < 1.2°`；**不达标就保留旧 `offL/offR`**（宁可不更新）。

4. 采样时同时要求 `gaze.valid`（现在完全没检查，`289`），并把 `blink` 从"软失败"改成"不进锚定样本"。
5. 首次也走同一套鲁棒规则，**不要**再靠 15° 的大窗口去兜模型的绝对偏置；
   死锁由已有的 `8 s` 超时兜底（`281`），不需要牺牲零位精度。
6. 顺手（同一改动的收益放大器）：refuel 期间隐藏 `drawHud`（`660-695`），

**验收**：连续 3 次加油，`anchorLeftDeg/anchorRightDeg` 的逐次变化 <0.5°；

结果卡片已有这两个字段（`app.ts:1156-1161`），不需要新增埋点。

### P2（次高）— 修滤波时序，并合并成一级自适应滤波

**怎么改**：

### P3（第三）— 难度曲线改成"按实测误差"，并加趋势门控的弱吸附

**改哪里**：捕获与寿命段（`src/game/gazeGame.ts:380-423`）、`spawn()`（`619-658`）。

**怎么改**：

1. 捕获半径不再由 `score` 决定：

4. 弱吸附（可选，最后做）：当"视线在最近 150 ms 内朝星星移动且速度 >2°/s"时，

"未移动命中率"（命中前 300 ms 视线位移 <1°）<5%；
`meanHitErrorDeg` 稳定在 3° 左右（不因难度变简单而升高）。
