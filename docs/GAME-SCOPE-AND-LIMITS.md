## 0. 一页结论

| 项 | 结论 |
| --- | --- |
| 产品定位 | **监督下的注视练习**。不是可独立使用的训练工具，不是测量工具，不是疗效证据。 |
| 能保证 | 星星出现时不会自动命中；火箭飞过星星不算；视线停在星星上能命中；"几乎没动就命中"会被记录并显示。 |
| 不能保证 | 头动、磁吸、滤波滞后、慢扫、近星停留这五条路径，都会在"没看星星"时被判中。它们来自"位置 + 容差"这个判定方式本身，不是偶发缺陷。 |
| 必须怎么做 | 成人全程在旁盯头部；单局 60 秒；命中率/得分只作参考；出现明显头动、未移动命中 ≥10%、有效帧 <90% 时作废该局。 |
| 最大的缺口 | 五条路径的实测数字全部来自离线回放，没有一条经过真实摄像头确认；结果卡还没有实机基线。 |

**三条不可跨越的红线**（展开见 §3.5）：

1. 游戏得分不是"注视精度"。容差 4.0–6.0°，大于要检测的效应。
2. 游戏数据不能和测量的 PD 数据放进同一张表比较。
3. 游戏不能用于宣布疗效。

## 1. 这个游戏现在保证了什么

四条，全部有断言或代码位置支撑。**每条都标了它的边界**——边界才是这一节的重点。

### P1 星星出现时不会自动命中

| 项 | 内容 |
| --- | --- |
| 证据 | `C9a–C9d`（撒点距离）、`C10a–C10c`（固定视线生命周期回放） |
| 数字 | 6 个固定视线位置 × 12 个星星生命周期 = **72 个，自动捕获 0 次**（C10a）；把趋势放大拉满到 6.0°、磁吸吃满 0.6° 的**最坏情况上界仍是 0 次**（C10c）；对照组（撒点退回修复前的随机方式）在同一模型下命中 **7 次**（C10b）——所以这个 0 不是把捕获关死了。 |
| 机制 | 撒点最小距离 = 最大捕获半径 + 1° = **7.0°**（`starSpawn.ts:15`、`gazeGame.ts:886-887`、`C9a` 1800 次撒点 0 违例） |
| **边界** | 只约束**星星出现的那一瞬间**。玩家自己把视线移到离星 6.0° 的位置之后，这条保证不再覆盖（见 N2）。 |

### P2 火箭的飞行路径不参与捕获判定

| 项 | 内容 |
| --- | --- |
| 证据 | `C12a-1` / `C12a-2` |
| 数字 | 复现审查记录中的 R1 反例（火箭 −7°、视线 +7°、星星 (0°, 5°)）。`C12a-1` 先证明**火箭的收敛路径确实进过捕获圈**（最近 5.01° ≤ 5.5°，旧判定会误命中）；`C12a-2` 同场景下 aim 判定 **捕获 0 次**（瞄准点全程最近 8.57°）。 |
| 机制 | 判定量是 `aim`（滤波后视线 + 磁吸偏移），火箭只是视觉载体（`gazeGame.ts:481, 500, 569-573`） |
| **边界** | 只管"火箭路过"。**视线自己**从星星旁边扫过仍会命中（N3、N4）。 |

### P3 视线停在星星上能正常捕获

| 项 | 内容 |
| --- | --- |
| 证据 | `C12d`、`C12e`（即审查记录中的 C2）；实际 GazeFilter 回放（H1–H7 同批） |
| 数字 | 视线从 −7° 移到星星并停住 → **捕获 1 次**（`C12d`）；再接**实际滤波器**重放同一段 → **234 ms** 命中。 |
| 机制 | 停留门控 `CAPTURE_DWELL_MS = 60`（`assist.ts:385`），按时间计、与刷新率无关。**计时从"进入 5.5° 圈"开始，不是从"到达星星"开始**：原始 gaze 回放的命中时刻是 184 ms（`C12e`），比视线真正落到星星（200 ms）还早 16 ms。 |
| **边界** | 反过来不成立：不停留也能命中（N4）。60 ms 是**下限**，不是"必须注视 60 ms 才算看过"。 |

### P4 "几乎没动就命中"会被记录并显示在结果卡

| 项 | 内容 |
| --- | --- |
| 证据 | `gazeGame.ts:588`（`isStillHit`，命中前 300 ms 内视线位移 <1°）、`app.ts:1174-1185` |
| 数字 | 结果卡显示 `未移动命中 x/y（z%）· 磁吸生效 n`；**z > 10% 时红字标"超过 10%，辅助过头"**（`app.ts:1175`） |
| 机制 | 只统计、不拦截 |
| **边界** | 只在"视线真的几乎不动"时触发；N1、N3、N4 全程视线在动，这个指标**抓不到**（见 §2.3 表）。 |

## 2. 这个游戏没有保证什么

### 2.1 为什么这五条不是"偶发 bug"

判定只有三个要素（`gazeGame.ts:548-573`）：

```
捕获半径 = min(分数上限 5.5°→4.0°, 1.6 × 最近命中中位误差) × 趋势放大(≤1.25)
           ↓ 硬顶 6.0°
条件 = |aim − 星星| ≤ 捕获半径，且连续满足 ≥ 60 ms
aim = 滤波后的视线 + 磁吸偏移（≤0.6°）
```

由此得到三条**结构事实**：

1. **容差比星星大 4.6 倍**。星星可视半径 1.2°（`gazeGame.ts:700`，`baseR = 0.05 × min(w,h)`），而开局捕获半径 5.5°。也就是说，判定范围从星星边缘向外延伸了 4.3°，那里的画面是黑的。
2. **容差与噪声同量级**。逐帧噪声地板 2–4.5°（校准交叉验证，`docs/STATUS.md:60`）。容差 5.5° ≈ 噪声的 1.2–2.8 倍——"偶然进圈"是常态。
3. **时间下限只有 60 ms**。60 ms + 5.5° 半径 ⇒ 正穿时弦长 11°，**任何慢于 183°/s 的扫过都会在圈内停留 ≥60 ms 而被判中**（11° ÷ 0.06 s = 183°/s）。

任何能让 `aim` 向星星推进 **≥0.4°** 的机制（0.4° = 撒点边界 7.0° − 最大容差 6.0° − 磁吸 0.6°，`C12f`），或让 `aim` 在圈里多停一会儿的机制，都会被判中。
下面五条分别是这些机制的实例，**每一条都是当前参数下的确定结果，不是概率事件**。

### 2.2 五条路径 + 一条降级路径

#### N1 头动绕过：只动头不动眼

| 项 | 内容 |
| --- | --- |
| 实测 | 头/判定点在 300 ms 内平移 **4.5°**，星星在 **7°** 外 → **534 ms 判中 1 次**（H1，实际 GazeFilter 回放） |
| 触发条件 | 头转 4.5°，仍在 `app.ts:415-417` 的 **5° 头位门控之内**，所以整帧 `valid`，门控不拦 |
| 机制 | 模型没有头位项（`model.ts:37-38` 明确写了"头位不进特征"）；头一转，虹膜在眼窝里的相对位置就变，`predMm` 整体平移，游戏把它当"视线动了" |
| 为什么是结构性的 | 判定看不到 `head`——`GameOptions.getGaze` 只返回 `{left, right, valid}`（`gazeGame.ts:64-65`），游戏层拿不到头位，无法区分"眼动"与"头动" |
| 谁能发现 | **只有人眼**。stillHits 抓不到（视线同时在大幅平移） |

#### N2 磁吸桥接：停在离星 6.0° 处不动

| 项 | 内容 |
| --- | --- |
| 实测 | 视线**静止**在离星 **6.0°** 处、噪声 σ=1°/样本（实测噪声量级）→ 磁吸把 aim 拉到 4.6° → **334 ms 判中 1 次**（H3） |
| 触发条件 | 玩家自己站到 6.0° 附近；磁吸的作用半径是 6.5°（`assist.ts:186`），覆盖得到 |
| 机制 | 磁吸门槛是"朝星星速度 ≥2°/s"（`assist.ts:195`）。滤波器给出的速度读数经过 1 Hz 低通（`gazeFilter.ts:41`），σ=1° 的帧间噪声在 **31% 的帧**上把读数顶过 2°/s（t4-F3 复算）。于是"静止不动"在代码眼里是"正在靠近" |
| 上限 | 磁吸偏移绝对量 ≤0.6°（`assist.ts:191`），且是**位置量不是积分量**，不会越吸越深 |
| 为什么是结构性的 | 撒点保证的 7.0° 只对"出现瞬间"有效。玩家移动到 6.0° 后，6.0 − 0.6 = **5.4° < 5.5° 容差** → 进圈。`C12f` 核算的 0.4° 余量（7.0 − 0.6 = 6.4 > 6.0）只防"自动"，不防"自己去站" |
| 谁能发现 | 部分：σ=1° 下 300 ms 内视线位移的期望约 1.4°，**多数情况超过 1°**，stillHits 不记录 |

#### N3 滤波滞后下的 pass-through：快速扫过不停留

| 项 | 内容 |
| --- | --- |
| 实测 | 视线以 **140°/s** 从 −7° 正穿星星到 +7°、不在星上停留 → 接**实际 GazeFilter** 时 **200 ms 判中 1 次**（H2）。同样 140°/s、但星星偏离路径 5.0° 时，原始 gaze 回放断言 0 次（`C12b`）——两者的差别在偏心距：正穿时弦长 11°、圈内停留 78.6 ms；偏心 5.0° 时弦长只有 4.58°、停留 32.7 ms，都按 60 ms 门槛切开 |
| 触发条件 | 一次普通的 14° 扫视（真实扫视常见 300–600°/s；140°/s 是慢速扫视/追随） |
| 机制 | 几何上已经足够：正穿 5.5° 圆的弦长 11°，140°/s → 圈内停留 **78.6 ms > 60 ms**。滤波只会把停留时间拉得更长，不是必要条件 |
| 不变量 | `C13a`（400°/s，圈内约 27 ms）→ 0 次；`C13b`（47°/s，圈内约 234 ms）→ 1 次。两个方向都有断言，语义固定 |
| 谁能发现 | **不能**。stillHits 只测位移 <1°，扫过时位移是 14° |

#### N4 慢扫判中：47°/s

| 项 | 内容 |
| --- | --- |
| 实测 | 47°/s 从 −7° 扫到 +7°、不在星上停留 → **1 次命中**（C13b）；接实际滤波器时 **234 ms**（H4，minAim 3.33°） |
| 数字依据 | 正穿弦长 11° ÷ 47°/s = **234 ms**；即使偏离星心 3.33°，剩余弦长 8.75° ÷ 47°/s = 186 ms，仍 > 60 ms |
| 为什么是结构性的 | 60 ms 的门槛只挡"快扫"，挡不住"慢扫"。而慢扫与"看住"在判定上无法区分——差别只在容差与时间的组合 |
| 谁能发现 | **不能** |

#### N5 近星停留：5.2° 处

| 项 | 内容 |
| --- | --- |
| 实测 | 视线在离星 **5.2°** 处（±0.6° 摆动）→ **66.8 ms 判中 1 次**（H5） |
| 数字依据 | 5.2° **本来就在 5.5° 容差之内**。60 ms 门槛 + 帧对齐 ⇒ 66.8 ms。摆动频率不改变结论（审查记录用 2 Hz）：距离本身已经在圈内，站住不动同样会在 60 ms 后判中 |
| 为什么是结构性的 | 星的可视半径 1.2°，判定半径 5.5°。玩家看着星星旁边 4° 的黑屏，判定认为"看住了" |
| 谁能发现 | 是：位移 <1° 时 stillHits 会计数 |

#### N6 撒点降级（低风险，会被记录）

| 项 | 内容 |
| --- | --- |
| 触发 | 火箭与瞄准点相距 ≥6° 的极端几何下，撒点从"同时避开两者"退化为"只避开瞄准点"（`starSpawn.ts:164-169`） |
| 记录 | `spawnRelaxed` 计数写进结果，卡片显示"撒点降级 N"（`app.ts:1178`） |
| 风险 | 降级时星星仍离**瞄准点** ≥7.0°，所以 P1 的不变量仍成立；它改变的是观感（星星会贴着火箭出现） |

### 2.3 逐条可利用性对照（N1–N5 + 降级项）

| # | 路径 | 需要玩家做到 | 命中耗时 | stillHits 能抓到吗 | 只有谁能发现 |
| --- | --- | --- | --- | --- | --- |
| N1 | 头动 4.5° | 转头，不动眼 | 534 ms | 否 | 成人观察 |
| N2 | 磁吸桥接 | 视线移到离星 6.0° 停住 | 334 ms | 多数否（位移 ≈1.4°） | 成人观察 |

### 2.4 结论与产品决策

这五条**不是实现缺陷**，是"位置 + 容差"判定方式的固有属性。消除其中任何一条都要改判定方式，而不是调参数：

- 消除 N3/N4/N5 → 提高停留门控或加位移门控，代价是正常命中变慢、真实注视被误伤；
- 消除 N1 → 引入头位锁定，代价是要改 UI 层传 head、有效帧下降；
- 消除 N2 → 判定改用磁吸前的 aim，代价是失去最后 0.6° 补足。

三条全做，容差仍然是星星半径的 4.6 倍。**产品决策：保留当前实现，把游戏定位为"监督下的注视练习"，得分只作参考，不追求防作弊。** 本文件就是把这个决策写成可交付的边界。

## 3. 监督使用规范（操作者）

> 只要能做到这一节的 6 条开始前检查 + 4 条进行中规则 + 作废判据，这个游戏就可以安全地当作练习使用。
> 本节不要求读者理解第 2 节的原理。

### 3.1 开始前（6 项，逐条打勾）

- [ ] **时长选 60 秒档**。界面有 60 / 120 / 180 三档（`index.html:166` 的 `gameDuration`），监督练习只用 60 秒档。
- [ ] **确认已校准**。没校准按钮会拒绝开始（`app.ts:1276`）。校准必须在**本局之前、同一坐姿、同一距离**完成。
- [ ] **距离与校准时一致**（本次配置示例 500 mm）。模型对距离敏感：瞳距偏差 **2%** 就整帧丢（`app.ts:424-428`）。起身、前倾、后仰都会让有效帧掉下来。
- [ ] **全屏**。游戏启动时自动请求（`gazeGame.ts:214`）。全屏失败也能玩，但 §4.2 的几何一致性没验证过。
- [ ] **眼镜按分视设置戴好**。选"无分视"时不做分视训练，只验证注视交互。
- [ ] **成人就位**：能同时看到孩子的侧脸和屏幕。这局里有些东西只有人眼能发现（§2.3）。

### 3.2 进行中（4 条）

1. **全程在旁，盯住头部。** 转头/歪头 4.5° 就能让 7° 外的星星在 534 ms 内被判中（N1）。这是唯一能拦住它的手段。
2. **只提醒，不指方向。** "往左看""星星在右上"这类口令会让孩子用头去找——直接命中 N1 的触发条件。
3. **不中途调坐姿、调距离。** 要动就中止，重新校准。
4. **加油阶段让孩子自己看中央绿圈。** 满箱 18 s、掉到 22% 触发，所以每 14 s 左右一次；加上找站与 3.2 s 加油，实际间隔 14–18 s，这段时间屏幕上没有星星。

### 3.3 结束后读 6 个数

结果卡（`app.ts:1153-1187` + 底部 meta 行 `app.ts:1473`）：

| # | 字段 | 位置 | 用途 |
| --- | --- | --- | --- |
| 1 | 得分 / 命中率 | 卡片第 1–2 行 | 只作参考。**不用于比较不同日期** |
| 2 | `未移动命中 x/y（z%）`、`磁吸生效 n` | "辅助护栏"行 | z > 10% 时卡片自己变红——这局判定被"不动也能中"钻到了 |
| 3 | `有效帧 XX%` | 卡片底部 meta 行 | 配合度的直接指标 |
| 4 | `锚定修正 左/右 x°` | "加油 / 锚定修正"行 | 任一眼 > 2° 标黄，说明坐姿或距离在漂 |
| 5 | `锚定降级` / `撒点降级 N` | "辅助护栏"行 | 零位或撒点走过降级路径，这局的数据要打标记 |
| 6 | `注视误差 中位 / P90`、`追上瞬间误差` | 卡片第 4–5 行 | 本局实际瞄准质量；与容差 4.0–6.0° 比对着看 |

**已知缺口**：第 1、6 项没有实机基线（本仓库至今没有一轮浏览器 + 摄像头对局）。第一次实机对局后回填本节。第 2、3、4 项的阈值是推导出来的（算术见 §3.4），不是实机基线。

### 3.4 什么情况下作废这一局

| 条件 | 怎么看 | 阈值 | 依据 |
| --- | --- | --- | --- |
| 明显头动 | 成人观察到 | 任何一次转头/歪头 | N1：4.5° 头动 → 7° 外的星 534 ms 判中 |
| 未移动命中偏高 | 卡片"辅助护栏"行 | `stillHits / hits ≥ 10%`（卡片红字） | `app.ts:1175`；目标 <5%，10% 是回退线 |
| 有效帧偏低 | 卡片底部 meta | `有效帧 < 90%` | 60 s、4 次眨眼 × 200 ms × 30 fps ≈ 24/1800 帧 = **1.3%**。掉到 90% 以下说明是头位/距离门控在连续丢帧，不是眨眼 |
| 坐姿移动 | 成人观察到，或锚定 | 锚定任一眼 `> 2°`（卡片标黄） | 2° 已接近实测命中误差 2.89°；`app.ts:1162` |
| 揉眼、流泪、频繁眨眼 | 成人观察到 | 任何一次 | 眨眼已是硬失败帧（`app.ts:407, 436`），频繁眨眼会同时抬高丢帧率 |

作废的含义：**该局只保留"做过练习"这个事实，不进入任何趋势比较，不与其他局平均。**

### 3.5 与测量模块的边界（三条红线）

**测量归测量，游戏归游戏。两者数据不可混用。**

| 项 | 测量模块 | 游戏 |
| --- | --- | --- |
| 产出 | 偏斜 PD、重复性、BCEA | 得分、命中率、stillHits |
| 精度依据 | 会话内重复性 **2.23 / 2.27 PD**（3 轮取中位，MDC95），前提是**同一份校准** | 无真值、无对照；判定容差 4.0–6.0° |
| 跨会话 | 偏置 **±5 PD**，绝对值不可跨天比较 | 同一局内不可比（容差随分数与命中误差变） |

**红线一：游戏得分不是"注视精度"。** 容差 4.0–6.0°，比要检测的效应大一个量级；得分高低主要由容差和撒点决定。

**红线二：游戏数据不能和 PD 放进同一张表。** 不得计算"命中率 vs 偏斜 PD"的相关，也不得用命中率替代任何 PD 指标。

**红线三：游戏不能用于宣布疗效。** 项目现状已明确：跨会话偏置大于要检测的效应、无棱镜对照、n=1（`docs/STATUS.md:69-75`）。游戏没有增加任何一条支撑证据。

**可以写进记录的**：本局是否配合（有效帧）、是否稳定（锚定偏差）、判定是否被钻空子（未移动命中率）。这三项是过程指标，不是结果指标。

## 4. 将来要变成"可独立使用的训练工具"需要什么

### 4.1 判定方式的三种改法（附代价）

当前判定 = `|aim − 星星| ≤ 容差`，持续 60 ms。下列三条各自消除一部分可利用路径，**没有一条能单独把游戏变成可独立使用的工具**。

| 改法 | 具体做法 | 消除哪条 | 代价 | 工作量 |
| --- | --- | --- | --- | --- |
| **A. 停留门控升级** | ① 停留 60 → 200 ms；② 停留期间要求视线位移 <1°；③ 开始计时的原始速度 >60°/s 则不计入 | N3、N4、N5（N5 部分） | 命中时刻整体后移 140 ms（234 → ≈374 ms），孩子"看到就抓"的节奏被打断；真实注视自带 0.1–0.5° 微扫视，位移门限 <0.5° 会误伤正常注视；需要重跑 C13a/C13b 与整套回放 | 0.5 天 + 回归 |
| **B. 头位锁定** | 判定期间要求 `|head − calibHead| < 1.5°` 且 `|Δhead| < 0.5°` | N1 | `GameOptions` 现在只给 `{left,right,valid}`（`gazeGame.ts:64-65`），要把 head 从 `app.ts` 传进游戏（动 UI 层）；1.5° 门限会让大量帧无效、有效帧显著下降；门限放宽则回到 N1 | 1–2 天 |
| **C. 判定用磁吸前 aim**（或直接删磁吸） | `gazeGame.ts:569` 改用 `aimBeforeMagnet`；磁吸只保留视觉 | N2 | 失去最后 0.6° 补足；对误差 2–4.5° 的用户（正是目标人群）命中率下降；`C12f` 的余量从 0.4° 变成 1.0°（7.0 − 6.0），仍需玩家不主动站到 6.0° | 0.5 天 |

**三条全做之后的残余问题**：容差 5.5° 仍是星星可视半径 1.2° 的 **4.6 倍**，"看着星星旁边 4° 的黑屏"依旧判中（N5 的机制不变）。要真正只认"看中"，容差必须压到 ≈2°，而那会回到审计里的"该中不中"（P3 的收益全部消失）。

**这意味着**：从"监督下的练习"走到"可独立使用的训练工具"，不是再调一轮参数，而是换判定范式（例如要求"两次独立注视都落在星上"或"注视点分布的质心落在星上且分布半径 <1.5°"）。代价是每颗星要 1–2 秒，60 秒一局的节奏需要重新设计。

### 4.2 一轮浏览器 + 摄像头完整对局（必须补的证据）

这轮对局的目的不是"手感好不好"，是把第 2 节的离线数字换成实机数字。**记录以下 6 项，缺一项这轮就不算完成。**

| # | 采什么 | 怎么采 | 判据 |
| --- | --- | --- | --- |
| 1 | **全屏几何（FM-8）** | 校准开始时、进入全屏后、游戏开始时各打印一次 `window.innerWidth/Height` 与 `canvas.width/dpr`；比较三者是否一致 | 三者相同 → 几何无缩放；不同 → mm 换算带缩放系数，先修 `runner`/`gazeGame` 的全屏时序，再谈判定 |
| 2 | **头动 → predMm 平移** | 受试者盯住中心点，仅转头 ±3°、±4.5°（不动眼），记录 predMm 位移 | 复现 H1 的"4.5° 头动 ≈ 4.5° 平移、7° 外星 534 ms 判中"，确认真实 MediaPipe 下的量级 |
| 3 | **真实扫视 pass-through** | 屏幕上左右两点来回扫（目标 140°/s、47°/s 两档），视线不落星 | 对照 N3/N4：若命中，说明离线结论在实机成立；若 0 次，说明实际滤波器比回放更保守，H2/H4 的结论要下调 |
| 4 | **stillHits / assistHits / validRatio 分布** | 至少 5 局，按 §3.6 记录 | stillHits 比例 <5% 为达标；≥10% 触发回退 |
| 5 | **眨眼/头动门控比例** | 统计 `quality.flags` 的分布（blink / yaw / pitch / tooFar / tooClose） | 正常眨眼应只占 1.3%（§3.4 的算术）。若 blink 单独 >5%，90% 这条线对眨眼过紧；若 blink <1% 而有效帧仍 <90%，丢帧来自头位/距离门控 |
| 6 | **一局完整 60 s 的帧率与推理耗时** | 记录 rAF 间隔分布与主线程阻塞 | MediaPipe 同步推理在主线程；若帧率掉到 30 fps 以下，滤波与判定时序的假设要重算 |

**同时要补的工程项**：把 H1–H7 的一次性复算沉淀成脚本。目前 `tools/assist-check.ts` 的 69 条断言里**没有** head 平移、实际滤波器 pass-through、磁吸桥接这三条——它们只存在于审查记录中，重跑不了。这是这轮对局之外最容易漏的一项。

### 4.3 儿童受试者的可行性

**时长预算（一次会话）**：热身 11 步 × 1.2 s = 13.2 s + 13 个校准点 × 1.3 s = 16.9 s + 验证点 1.4 s ≈ **32 s**（一轮校准；触发坏点补测再加 2–5 s），加游戏 60 s + 2–3 次加油 × 3.2 s ≈ **105–115 s 净时长**。这是"能不能坐住"的第一道门槛。

**准入条件**：能独立完成 13 点校准，且该局有效帧 ≥90%。达不到的儿童不进入游戏，先做配合度筛查。

**硬件前提**：分视训练需要红青/红绿/红蓝滤片，且滤片要能戴在儿童脸上。眼镜状态会改变关键点检测（`docs/STATUS.md:83` 记录了这是未测的域偏移）。

**伦理前提**：未成年人需监护人知情同意；本工具未做临床验证，当前只有开发者本人 n=1（`docs/STATUS.md:74`）。

**样本要求**：n ≥ 3 名儿童，结果与成人数据分开报告；不得合并统计。

**必须先于儿童做的**：4.2 的实机对局。用未验证的判定去测儿童，得到的数据不能解释。
